# Work that runs without you

_Generated from the course source. Do not edit this file by hand._

Outcome: The first process to automate, written as a spec someone can build from. About 35 minutes.

When every piece of recurring work needs a person to start it in Claude, that person's usage becomes the ceiling. The usual response is to buy more seats or more credits. That is not the fix. Each person has their own allowance, so a new seat for someone else does nothing for the person who keeps hitting the limit, and extra credits pay for the same inefficient setup.

The fix has two parts. First, find out what is really causing the limits. Second, take recurring work out of the chat and turn it into a process that runs on its own, on a schedule or when something happens, with a person approving only where it matters.

This module ends with a written spec for the first process. Writing the spec is easy. Building it is medium to hard, depending on the route, and the last step says so.

Official pages to check during this module:

- Scheduled tasks: https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork
- What uses up a person's allowance: https://support.claude.com/en/articles/9797557-usage-limit-best-practices
- Usage credits and spend limits: https://support.claude.com/en/articles/12005970-manage-usage-credits-for-team-and-seat-based-enterprise-plans

## processes.schedules: Count scheduled tasks and the recurring work a person still has to start

### Ask

A scheduled task is a job a person has set up in Claude to run on a timetable, such as a daily briefing or a weekly report.

1. "Open **Scheduled** in the left sidebar. How many scheduled tasks do you have? Read me what each one does, in a few words."
2. "Who else on the team has scheduled tasks, and roughly how many each?"
3. "Which pieces of work come round every day, week or month where a person opens Claude and starts it by hand?"
4. For each: "Who starts it, how often, and how long are they tied up?"
5. "How many pieces of recurring work run today with nobody starting them, in any tool?"

### Do

Build one list of recurring work.

| Work | How it starts today (scheduled task / by hand) | Whose account | How often | Minutes of a person's time per run | Services it touches | Result goes to |
| --- | --- | --- | --- | --- | --- | --- |

- Count the scheduled tasks per account. 10 or more scheduled tasks on one account is the point this audit treats as a signal: that person's Claude has become a place where the company's processes run, and it is time to move them into automations that do not depend on one account.
- Scheduled tasks are still tied to one person's account and plan. Do not state whether or how they count against that person's allowance; the help page does not say. If it matters, the person checks **Settings > Usage** before and after a run.
- The person sees only their own scheduled tasks. Colleagues' numbers are estimates; mark them so.
- Record the answer to question 5 as today's figure for "processes that run without a person starting them".

### Done when

- The list has the person's scheduled tasks and at least three pieces of recurring work started by hand, or the person has confirmed there are fewer.
- The number of scheduled tasks per account is written down, with estimates marked.
- Today's count of processes that run on their own is recorded.

### Mark blocked when

- The recurring work belongs to colleagues and the person cannot describe it. Give them the table headings to take away.

### Summary to report

State the counts. Example: "14 scheduled tasks on one account and about 20 more across the team (estimate). Nine pieces of weekly work are started by hand. Two processes run today without a person starting them."

## processes.limits: Find who hits usage limits and what causes it

### Ask

1. "Who hits usage limits? Roles, and how often."
2. "What are they doing when it happens? Describe a typical session."
3. "In those sessions: how many connectors are switched on, and how long do the conversations run?"
4. "Do they retype the same long instructions each time, or is there a skill for that work?"
5. "Which model do they use for routine work?"
6. "What has the company done about it so far: more seats, higher seats, extra credits, nothing?"

### Do

Limits are usually caused by how the work is set up, not by too few seats. Check each cause and mark it yes, no or not known. Open the usage page listed at the top of this module and confirm what counts today.

| Cause | Present? | Fix | Difficulty | Where it is dealt with |
| --- | --- | --- | --- | --- |
| Many connectors switched on in every session | | Switch off what the session does not need; set tool access to On demand | easy | `connectors` |
| Connectors that return far more than the work needs | | Custom connectors for the main services | hard | `connectors` |
| Very long conversations instead of a new chat per task | | Start a new chat for each task | easy | here |
| Large or unused files in the project | | Remove files nobody uses; keep changing data out | easy | `foundations` |
| The same long instructions retyped, no skill | | Build a skill from the senior person's method | easy | `skills` |
| No shared way of working: everyone prompts differently | | Standardise with skills and plugins; for long multi-part jobs, split the work between sub-agents where the tool supports it | medium | `skills` |
| The most capable model used for routine work | | Use a lighter model for routine work | easy | here |
| Recurring processes run by hand or as scheduled tasks on one person's account | | Move them out of the chat | medium to hard | this module |

Then:

1. Show the table with only the causes that are present.
2. Fix the two "here" causes now, if present: agree the habit and tell the heavy users.
3. Say plainly whether more seats would help. Each member has their own allowance and it cannot be shared, so seats help only when new people need access, not when the same people run out. Extra usage keeps people working but does not remove the cause.
4. Record two figures by role, not name: who hits limits and how often. If the person is willing, pick one typical task, have them look at **Settings > Usage** before and after doing it once, and note the rough change. This is the starting point for "usage spent per finished task". It is a rough reading, not a measurement.

### Done when

- Each cause is marked yes, no or not known.
- Who hits limits, how often and during what kind of work is recorded by role.
- The person has heard a plain answer on whether more seats would help.

### Mark blocked when

- The heavy users are not here and the person cannot describe their sessions. Give them questions 2 to 5 to pass on.
- Nobody hits limits. Mark the step `skipped`, not `blocked`, and say so.

### Summary to report

State who hits limits and the causes found, by role. Example: "Three analysts hit limits weekly during long reporting sessions. Causes found: 24 connectors on, heavy responses from two services, no skill for the report, four processes run by hand. More seats would not help."

## processes.pick: Rank the candidates and pick the first

### Ask

- "For this one, if it ran on its own and got it wrong, what is the worst that happens before someone notices?"
- "What starts it: a time, or something happening, such as a new record or an incoming email?"
- "Does it always follow the same steps?"
- "Where would a person still want to approve before anything is sent or changed?"
- At the end: "I suggest we spec [process] first. Do you agree?"

### Do

Score each piece of recurring work from `processes.schedules`. Add these columns and show the table.

| Work | Hours of a person's time per month | Clear trigger? | Same steps each time? | Inputs reachable by a system? | Damage if wrong | Good candidate? |
| --- | --- | --- | --- | --- | --- | --- |

A good first candidate has all of these:

- It runs often and ties up a person each time.
- It has a clear trigger: a time, or an event in a system.
- It follows the same steps each time. If it needs judgement at one point, that point can be an approval.
- Its inputs live in systems that an automation can reach, not in someone's head or on paper.
- A mistake would be noticed and cheap to fix, or a person approves before anything leaves the company.

Pick the candidate with the most hours among those that meet all five. Name the runner-up. Do not pick a process that moves money or makes commitments on its own as the first one, however many hours it takes.

Work that needs a person's judgement throughout is not a process to automate. It stays in Claude, with a skill. Say so for those rows.

### Done when

- Every piece of recurring work has a score and a yes or no.
- One process is chosen, the person agrees, and a runner-up is named.

### Mark blocked when

- No candidate meets all five conditions. Say which condition fails most often; that is the thing to fix first.
- The person cannot decide without the team that does the work.

### Summary to report

State the kind of process chosen and why, in general terms. Example: "Ranked nine pieces of recurring work; five are good candidates. First: the weekly client status report, about ten hours a month, clear trigger, a person approves before sending. Runner-up: invoice reminders."

## processes.spec: Write the spec: trigger, inputs, steps, checks and owner

### Ask

1. "What exactly starts it: which day and time, or which event in which system?"
2. "What does it need to read, and from where?"
3. "Walk me through the steps as you do them today, in order."
4. "How do you know a run went right? What do you check?"
5. "What should happen when something is missing or looks wrong?"
6. "What must a person still approve, and who?"
7. "Who owns this process once it runs: who gets told when it fails?"
8. "Does the company already use an automation tool or have a developer?"

### Do

Write the spec and show it. It must be clear enough that someone who was not in this conversation could build from it. No client names, no credentials, no real data.

```markdown
# Process spec: [name]

Date: [date]. Owner: [role]. Written for: whoever builds it.

## Purpose
[One or two sentences: what this produces, for whom, and what it replaces.]

## Trigger
[Every Monday at 08:00 / when a new record appears in (system) / when an email arrives at (shared inbox).]

## Inputs
| Input | Comes from (system) | Fields needed | Access needed |
| --- | --- | --- | --- |

## Steps
1. [Read ...]
2. [Work out ...]
3. [Draft ...]
4. [Check ...]
5. [Send to approver / save to ...]

## Where Claude is used
[Which steps need a model: for example drafting the summary. Which skill holds the method, if one exists.]

## Checks
- [What makes a run valid: for example every record has an owner and a date.]
- [What makes it stop: for example an input is empty or older than a day.]

## What a person still approves
- [Step]: approved by [role] before [it is sent / anything is changed].

## When it fails
[Who is told, how, and what they do. What happens to that run.]

## Output
[What is produced, in what format, and where it goes.]

## How we will know it works
- Runs without a person starting it: [yes, on what schedule].
- A person's time per run: [minutes today] -> [minutes to approve].
- First month: [role] reviews every run.

## Route
[n8n or Zapier / a cloud setup], because [reason].
```

Choose the route with the person and give one neutral sentence on each:

- **n8n or Zapier.** These are tools for building automations from ready-made steps between common services; they are quicker to set up and easier for a non-developer to look after, and suit processes made of standard steps.
- **A cloud setup**, for example on Cloudflare or Vercel or another cloud provider. This is code that runs on a schedule or on an event; it handles heavier or more unusual work and gives more control, and it needs a developer to build and look after it.

If the steps are standard and the services are common, the first route usually fits. If the process needs custom logic, large volumes or tight control over data, the second does. Record the choice and the reason. If the person cannot tell, write "to be decided by whoever builds it".

Name the hard part plainly. The spec is the easy half. Building the process outside the chat, connecting it to the company's systems and trusting it to run on its own is the hard half. On the first route it is medium: someone comfortable with such tools can do it. On the second it is hard. Either way, this needs someone technical. Say who that could be inside the company, or record that nobody is named yet.

### Done when

- The spec has a trigger, inputs, steps, checks, an owner, what a person still approves, and a route with a reason.
- The person has read it and agrees that someone else could build from it.
- The person has been told which part is hard and who could do it, or that nobody is named.

### Mark blocked when

- The steps are not agreed among the people who do the work. Someone has to settle the method first.
- The inputs sit in a system nobody here can describe, and its administrator is not available.
- Nobody can be named as the owner of the process.

Having nobody technical to build it does not block this step. The spec is the outcome; record the gap in it.

### Summary to report

State that the spec exists, the route and who builds it, in general terms. Example: "Spec written for the weekly client status report: time trigger, three inputs, five steps, one approval before sending. Route: n8n or Zapier. Needs someone technical to build; nobody named yet."
