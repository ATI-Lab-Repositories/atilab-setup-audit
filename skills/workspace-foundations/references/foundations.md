# Foundations

_Generated from the course source. Do not edit this file by hand._

Outcome: A company context file, tidy projects, one page of usage rules and a way to bring people on. About 45 minutes.

Four things that every other improvement rests on: one short file that tells Claude about the company, a small number of well-kept projects, one page of rules, and a simple way to get people started. All four are easy. The person can finish them with you.

## foundations.context: Write and install the company context file

### Ask

Claude starts every chat knowing nothing about the company. This file fixes that. Ask these one at a time. Skip a question if an earlier answer covered it. If an answer is vague, ask once for a concrete example, then move on.

1. "In one or two sentences, what does the company do, and for whom?"
2. "What do you sell? List the main products or services the way you would say them to a customer."
3. "Who are your customers? Describe the types, not the names."
4. "Walk me through one normal job from first contact to finished. What are the stages called inside the company?"
5. "Which teams or roles are there, and what is each responsible for? Roles only, no names."
6. "Which words, abbreviations or product names would confuse a new starter? Give me each one and what it means."
7. "How should writing from your company sound? Paste two or three sentences you are happy with, with any names removed."
8. "Which formats do you always use? Date format, currency, spelling (UK or US), units, how you write the company name."
9. "What must Claude never do or say on the company's behalf? For example: quote a price, promise a delivery date, give legal advice, name a client."
10. "Where does the true answer live for prices, stock, customer records and policies? Name the system or document for each, so Claude can say 'check X' instead of guessing."
11. "Who should a colleague ask when Claude is unsure? Give a role or a shared inbox, not a personal address."
12. "Is there anything else a new colleague is told in their first week that we have not covered?"

If the person offers an existing document (an "about us" page, a handbook intro, a brand guide), use it to answer questions before asking them. Ask them to remove names, prices and anything confidential first.

Then: "Where does your team use Claude most, and is there a shared project the team works in?"

### Do

Write the file from the answers, using the template. Keep the headings. Delete a section only if the person has nothing for it.

- One to two pages. Claude reads it at the start of every chat in the project, so every line must earn its place.
- Short, direct statements in the person's own words. "We write dates as 3 March 2027."
- Only what is true for the whole company and stays true for months. No client names, no personal data, no prices or figures that change, no passwords or keys.
- Write rules as plain instructions with the reason: "Do not quote prices. Prices change weekly; point people to the price list."
- Mark every gap as `TO DECIDE:`. Do not guess.

```markdown
# Company context: [Company name]

Last reviewed: [date] by [role]. Review every three months.

## What we do
[One or two sentences: what the company does and for whom.]

## What we sell
- [Product or service]: [one line, in the words used with customers]

## Who our customers are
- [Customer type]: [what they need from us]

## How a job runs
1. [Stage name]: [what happens, which team]
2. [Stage name]: [what happens, which team]

## Teams and what they own
- [Team or role]: [responsible for]

## Our words
| Term | Meaning |
| --- | --- |
| [Term or abbreviation] | [Plain meaning] |

## How we write
- Tone: [three or four words, for example: plain, warm, direct]
- We say: "[short example sentence in the house style]"
- We do not say: "[phrase or style to avoid]"
- Formats: dates as [format]; currency as [format]; spelling [UK/US]; company name written as [exact form].

## Rules for Claude
- Do not [action]. [Reason, and what to do instead.]
- Always [action] before [situation].
- If you are not sure, say so and name who to ask (see below). Do not guess.

## Where the true answer lives
| Question | Look here |
| --- | --- |
| Prices | [system or document] |
| Customer records | [system] |
| Policies | [document or folder] |

## Who to ask
- [Topic]: [role or shared inbox]
- Anything not covered here: [role or shared inbox]
```

Show the full draft, apply changes and show it again until the person approves. Then install it:

1. **Master copy.** The person saves the approved file somewhere the company controls, such as a shared drive. Create the file for them if you can.
2. **Project instructions.** In the Claude app: open **Projects**, open the team's project or choose **+ New Project**, choose **Set project instructions**, paste the whole file, choose **Save instructions**. Project instructions apply only to chats inside that project, so the file goes into each project the team uses. Do the main one now and list the others.
3. **Sharing.** On Team and Enterprise plans, choose **Share project** and give **Can edit** only to whoever owns the file. Everyone else gets **Can view**.
4. **Claude Code.** Put the content in the project's `CLAUDE.md`, or in a file that `CLAUDE.md` refers to. If you are running in Claude Code and the person agrees, write it yourself.

Run one quick test. In a new chat inside that project, the person asks a real question from this week that uses one of the company's own words and touches one of the rules. If the answer gets the word wrong or breaks the rule, fix the line that caused it, save both copies and ask once more.

### Done when

- The person has read and approved the whole file, and it holds no client names, personal data or credentials.
- A master copy is saved where the company controls it.
- The file is installed as instructions in at least one project the team really uses, and other projects that need it are listed.
- One real question, asked in a new chat in that project, was answered using the company's words and rules.

### Mark blocked when

- The person cannot answer questions 1, 2, 3, 6, 9 and 10 and the colleague who can is not here.
- The person cannot edit the instructions of the project the team uses. Give them the file to pass to the project's owner and say exactly where it goes.
- Someone else must approve the wording and is not available.

A few answers marked `TO DECIDE:` do not block the step.

### Summary to report

State that the file exists, where it is installed and the test result. Do not include any text from the file. Example: "Context file written and approved, about one page, saved as instructions in one shared project. Test question answered correctly. Two items still to decide; two more projects listed."

## foundations.projects: Merge tiny projects and take changing data out of project files

### Ask

1. "Read me your projects: for each, what it is for, roughly how many files it holds and who uses it."
2. "Which of these share the same background documents?"
3. "Which files hold things that change: monthly figures, statistics, current targets, this week's task list?"
4. "Which projects has nobody opened in the last couple of months?"

### Do

Build a table and show it.

| Project | Used for | Files | Who uses it (roles) | Same background as | Changing data inside? | Decision |
| --- | --- | --- | --- | --- | --- | --- |

Apply three rules and explain each in a sentence:

- **Fewer, fuller projects.** A project should match a team or a kind of work, not one task. Many tiny projects each carry their own copy of the same background, and the copies drift apart. Merge projects that share background into one, with the company context file as its instructions.
- **Reusable context only.** Project files are for things that stay true: how the company works, templates, reference documents. They are read into chats in that project and count toward what each chat can hold, so remove files nobody uses.
- **No changing data.** Metrics, statistics, temporary tasks and goals do not belong in project files. They go out of date and Claude treats them as true. Keep them in the system they live in. Claude reads them through a connector when needed, or the person pastes the current figure into the chat.

Mark each project **keep**, **merge into [project]** or **archive**. Prefer archive to delete: an archived project keeps its content.

The person makes the changes. Do the first merge together: move the useful files, set the instructions, archive the emptied project. List the rest with who will do them.

### Done when

- Every project has a decision.
- At least one merge or archive is done, and the rest are listed with an owner.
- Files with changing data are removed or listed for removal, with a note of where the live figure comes from instead.

### Mark blocked when

- The projects belong to other people and the person cannot change or archive them. Give them the table to share.
- A team must agree before its projects are merged and nobody from that team is here.

### Summary to report

State the counts before and after. No project names. Example: "38 projects reviewed: 6 kept, 9 merged into 3, 23 to archive. Four files with monthly figures removed. First merge done; the rest assigned to two team leads."

## foundations.rules: Write the usage rules, set approvals for write actions and a spend cap

### Ask

1. "What should people use Claude for first?"
2. "What must never go into it? Think of payroll, health details, card numbers, anything a client contract restricts."
3. "Does a person always check Claude's output before it leaves the company?"
4. "Who approves a new connector, and who should someone tell if something went in that should not have?"
5. "For actions that send, change or delete things in your other systems: should a person approve each one?"
6. "What is the most you are willing to spend on extra usage in a month, for the whole organisation?"

### Do

Write the rules on one page and show them.

```markdown
# How we use Claude

Last reviewed: [date] by [role].

## Use it for
- [Kind of work]

## Do not put in
- [Type of information]
- Passwords, keys or recovery codes, ever.

## Always
- Check the output before it leaves the company. You are responsible for what you send.
- Use your own company account. Do not share logins.
- Work in the shared project [name] so Claude has the company context.

## Connectors
- Approved connectors: [list]. New ones are approved by [role].
- Actions that send, change or delete need a person's approval each time.

## Shared things
- Company context file: owned by [role].
- Skills: owned by [role per team]. Report a bad result to them.

## Help
- Stuck or unsure: ask [role or channel].
- Something went in that should not have: tell [role or shared inbox] the same day.
```

Tell the person this is a working set of rules, not legal advice. Where a rule depends on a contract or a regulation, mark the line `TO CONFIRM:` and record who owns that question.

Then two settings. An owner makes both changes; you say where.

- **Approvals for write actions.** Under **Organization settings > Connectors**, open a connector, then its **Tools** tab. Each tool or group of tools can be set to **Always allow**, **Needs approval** or **Blocked**. Set tools that send, change or delete to **Needs approval**, and block delete unless there is a named need. The setting applies to everyone and members cannot override it. Say this before the owner changes it.
- **Spend cap.** Under **Organization settings > Usage**, owners manage extra usage and spend limits. Agree an organisation-wide monthly cap and start low. Which caps exist depends on the plan, so follow the usage credits page listed at the top of this module. Do not ask for billing details.

Record the settings as they are now, who can change them and a date to review after the first month.

### Done when

- The rules page is approved and saved where the team can find it, with an owner.
- Write actions on each connector are set to need approval, or the change is listed for an owner.
- A monthly spend cap is set, or the person has decided not to allow extra usage, or the figure is agreed and passed to an owner.

### Mark blocked when

- The person is not an owner and cannot open the organisation settings. Give them the two changes and the agreed figure to pass on.
- The rules need sign-off from someone who is not available.
- Nobody here knows the company's obligations to clients or regulators well enough to write the "do not put in" list.

### Summary to report

State what was written and set, without amounts. Example: "One-page rules approved: three uses, four things never to put in. Write actions set to need approval on five connectors. Monthly spend cap set; review in one month. One line waiting on contract review."

## foundations.onboarding: Name a champion, plan 1:1 sessions and choose the first skill people start on

### Ask

1. "Who is the one person colleagues will go to with questions? They need time each week and the patience for basic questions."
2. "How much time can they give each week for the next month?"
3. "Who are the first five to ten people to bring on? Pick people whose work Claude can help with."
4. "Is there a skill that already works well, one that gives a good result the first time someone uses it?"
5. "When can each of those people sit down for half an hour, one to one?"

### Do

Adoption rarely comes from a group training. It comes from three things. Set up each one.

- **A champion.** One named person who owns adoption, answers questions and collects what does not work. Record the role and the weekly time. If nobody can do it, say plainly that adoption will stall without one. Do not invent one.
- **One-to-one sessions.** Half an hour each, champion and one colleague. The colleague brings a real task from their week. They can ask the basic questions they would not ask in a group. Together they take that task from nothing to finished, so the colleague sees the whole route once. Book the first sessions with real dates.
- **A first skill that already works.** Start each person on an established skill, so the first thing they see is high-quality work with little effort. If the company has none yet, use the first skill from the `skills` module when it exists and note that the sessions wait for it.

Write the plan on half a page and show it.

```markdown
# Getting people started with Claude

Champion: [role], [hours] a week. Questions go to: [channel].

## First group
[Count] people from [teams]. One-to-one sessions booked between [date] and [date].

## Each session (30 minutes)
1. The colleague brings one real task.
2. Open the shared project. Run the first skill once: [skill name].
3. Do the colleague's own task from start to finish.
4. Note what was confusing or went wrong. The champion fixes the context file or the skill.

## Check after four weeks
- How many of the first group used Claude every week?
- Which task does each person now do with it?
- Next group: [who], starting [date].
```

### Done when

- A champion is named with time set aside.
- The first group is named and at least the first sessions have dates.
- The first skill is chosen, or the plan says which skill it waits for.

### Mark blocked when

- Nobody has the time or the standing to be the champion.
- The first group's manager has not agreed to free their time.

### Summary to report

Use roles and counts only. Example: "Champion: the operations lead, two hours a week. Eight people in the first group, one-to-one sessions booked over two weeks. They start on the weekly status skill. Check after four weeks."
