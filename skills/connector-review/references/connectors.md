# Connectors

_Generated from the course source. Do not edit this file by hand._

Outcome: A table of what Claude can read and change, unused access closed, and the heaviest connectors named. About 40 minutes.

A connector links Claude to another service, such as email, a shared drive or a CRM, so Claude can read from it and sometimes change things in it.

Connectors cause two different problems. The first is access: what Claude can read and change, and whether a person approves the changes. That part is easy to fix in settings. The second is weight. Many general-purpose connectors answer a simple request with a crowded response: metadata, tags, headings and fields nobody asked for. All of it lands in the session, fills the space the conversation has, and uses up the person's allowance. Trimming helps a little. The real fix is a connector built for how the company uses that service, and that is a build job.

You will not ask for any passwords, keys or tokens in this module.

Official pages to check during this module:

- Connectors, tool access and permissions: https://support.claude.com/en/articles/11176164-use-connectors-to-extend-claude-s-capabilities

## connectors.inventory: List every connector and how many load in a normal session

### Ask

1. "Here are the connectors I can see in this session. Is that your normal set?" If you cannot see them: "Open **+** in the message box and hover over **Connectors**. Read me the list and which are switched on."
2. "Are you an owner of the Claude organisation? If so, open **Organization settings > Connectors** and read me what is enabled for everyone."
3. "Did anyone add a custom connector, one set up with a web address rather than picked from the list?"
4. "Does anyone run connectors on their own computer, for example in the desktop app or Claude Code?"
5. For each connector: "Who uses it, for what, and how often?"

### Do

Start from your own list of connected tools in this session, if you can see it. Do not call any connector yet. Build the table. Roles, not names.

| Connector | Type (directory / custom / local) | Loads in a normal session? | Who uses it (roles) | Used for | How often | Still needed? |
| --- | --- | --- | --- | --- | --- | --- |

- Count the connectors that load in a normal session. More than 20 connectors in one session is over the limit this audit uses. Say so and say why: each one adds its tool descriptions, and the session gets crowded before any work starts.
- Note the **Tool access** setting if the count is high (**+ > Connectors > Tool access**: Auto, On demand or Always available). Anthropic's help page suggests On demand from about ten active connectors.
- Connectors that someone runs on their own machine are not covered by the organisation's connector settings. List them separately.
- Mark anything nobody can explain as "unknown owner".
- Mark the three services the team uses most. They are needed in `connectors.weight`.

### Done when

- Every connector the person can see is in the table with its type, users and whether it loads in a normal session.
- The number that load in a normal session is written down.
- The top three services are marked.

### Mark blocked when

- The person is not an owner and cannot see the organisation-wide list. Record what they see for themselves, mark the step `blocked`, and say that an owner needs to read out the organisation list.
- Connectors are managed by an outside IT provider who is not in the session.

### Summary to report

State how many connectors were found by type and how many load in a session. Do not list which systems are connected. Example: "Found 26 connectors: 22 from the directory, 3 custom, 1 run locally. 24 load in a normal session, over the 20 mark. Two have no known owner."

## connectors.access: Note what each one can read and change, and close what nobody needs

### Ask

For each connector, one at a time:

1. "Open the connector's list of tools. What can it read? What can it create, change, send or delete?"
2. "For each of those, is it set to always allowed, needs approval, or blocked?"
3. "In the connected service itself, what can the people who use this connector see: everything, or only their own files and records?"
4. For custom connectors: "Does everyone sign in with their own account, or does it use one shared login?"

Then: "Here is what I suggest changing, one line per connector. Which do you agree with?" Before each change: "Shall we do this one now? You make the change; I will tell you where." After it: "What does the setting show now?"

### Do

Add to the table.

| Connector | Can read | Can change (create / edit / send / delete) | Setting for changes | Whose permissions apply | Risk note | Change agreed |
| --- | --- | --- | --- | --- | --- | --- |

How access works, per the connectors help page at the time of writing: when each person signs in with their own account, Claude reaches only what that person can already reach in the connected service. A custom connector that uses one shared credential reaches whatever that credential allows, for everyone who uses it.

Write a risk note where Claude can send, delete or overwrite without approval; where a shared credential gives everyone the same wide access; where the connector reaches personal, health, payroll or client-confidential data; or where nobody can say what the connector does.

Propose changes with these defaults:

- **Not needed**: disconnect it. A person does this in their own connector list. An owner can turn it off for everyone under **Organization settings > Connectors**.
- **Read is needed, changes are not**: an owner sets the write and delete tools to **Blocked** on the connector's **Tools** tab.
- **Changes are needed**: set them to **Needs approval**, so a person confirms each one.
- **Delete**: block it unless there is a specific, named need.
- **Shared credential**: ask whether each person can sign in with their own account instead. If not, narrow what the shared login can reach in the connected service.
- **Access too wide in the connected service**: that is fixed in the service, not in Claude. Record who administers it.

Organisation-level tool settings apply to everyone and members cannot override them. Say this before an owner changes one. The person makes every change themselves. After each, update the table.

### Done when

- Every connector has its read access, change access and current settings recorded.
- Each risk note has a decision: changed, accepted with a reason, or assigned to a named role.
- Changes still to make are listed with who makes them.

### Mark blocked when

- The person is not an owner and cannot see or change the tools of a connector. Give them the list of changes to pass to an owner.
- A custom connector has no documentation and nobody here knows what login it uses.
- A change would stop work that depends on the connector and the person needs to check with that team first.

If some changes were made and others wait on someone else, mark the step `blocked` and say what is outstanding.

### Summary to report

State how many connectors can change data, what was closed and what is waiting. No system names. Example: "26 connectors reviewed; 11 can change data, 4 of them without approval. Disconnected 6 unused, set write tools to need approval on 4. Two changes wait on the owner."

## connectors.weight: Test your top three services: how much comes back and how much is used

### Ask

For each of the three most-used services, one at a time:

1. "What is one typical thing you ask Claude to get from this service? Pick a real, everyday request that only reads."
2. "For that request, what do you actually need back? For example: the status and owner of five records, or the text of one document."
3. "Shall I run it, or would you rather run it yourself and describe what comes back?"

### Do

This is a rough judgement, not a measurement. Say so before you start. You cannot count exactly how much of the session a response takes, and one request is not a study. It is enough to see whether a connector returns roughly what is needed or many times more.

For each service:

1. Agree the request and what is needed from it. Read-only requests only.
2. Run it once if you have the connector in this session and the person agrees. Otherwise the person runs it in their own chat and describes what came back.
3. Compare what came back with what was needed. Look for whole records where three fields were needed; long lists where five items were needed; metadata, internal ids, tags, formatting and headings; several calls to get one answer.
4. Record a short "returned versus used" note in your own words, with a rough size: **about right**, **several times more than needed**, or **far more than needed**. For example: "Asked for the status of five records. About three pages came back, including every field of each record. Four lines were used."
5. Note how many tools the connector exposes and how many the team uses.

Never record the data itself: no record contents, names, figures or document text, in the table or in the summary. Write only the kind of thing that came back and how much. Do not keep the response; once you have judged it, move on.

| Service | Typical request (in general terms) | Needed | Came back | Returned versus used | Tools exposed / used |
| --- | --- | --- | --- | --- | --- |

Rank the three from heaviest to lightest.

If the person wants a second opinion on a heavy one, they can run the same request again and look at **Settings > Usage** before and after. That is still rough.

### Done when

- Each of the top three services has one request tested, or a stated reason why it was not.
- Each has a "returned versus used" note with a rough size, and no data from the service is written down.
- The person has seen the ranking and been told it is a rough judgement.

### Mark blocked when

- Neither you nor the person can run a request against a service in this session.
- The person is not allowed to run test requests against a service that holds sensitive data. Skip that service and say so.

### Summary to report

State the ranking by kind of service, without the data or the system names. Example: "Three services tested with one everyday request each. Two returned far more than needed, one about right. Rough judgement from single requests, not a measurement."

## connectors.plan: Record which connectors to trim, keep or replace

### Ask

- "Here is what I suggest for each connector: trim, keep or replace. Do you agree?"
- "For the ones marked replace: is there someone technical, inside the company or outside, who could build this?"

### Do

Give every connector one of three decisions and write the plan.

- **Trim** (easy). Switch it off in sessions that do not need it. Disconnect it if nobody uses it. Set **Tool access** to **On demand** when many connectors are active. Have an owner block the tools nobody uses. Do the trims now with the person where they can.
- **Keep.** It is used, it returns roughly what is needed, and its access is under control.
- **Replace** (hard). A top service whose connector returned far more than needed and that the team uses every day. The replacement is a custom connector: a small service, built for the company, that returns only the fields the work needs and offers a few tools named after what the team does. Once two or three of those exist, the next step is one entry point in front of them, sometimes called an MCP portal: a single connector that exposes a handful of tools shaped around how the team works across those services. That keeps sessions light and makes work that crosses several systems more reliable.

```markdown
# Connector plan

Date: [date]. Connectors in a normal session: [number now] -> [number after trimming].

| Connector | Decision | What to do | Difficulty | Who |
| --- | --- | --- | --- | --- |
| [name] | Trim | [switch off by default / disconnect / block unused tools] | easy | [role] |
| [name] | Keep | - | - | - |
| [name] | Replace | Custom connector returning only: [fields the work needs]. Tools: [two to five actions the team does]. | hard | [technical owner, or "not yet named"] |

## For whoever builds the replacements
- Services, in order: [1], [2], [3].
- For each: the everyday requests, what is needed back, and what came back today (from the weight test).
- Later: one entry point in front of the custom connectors.
```

Name the hard part plainly. Trimming is worth doing today, and it gives a modest improvement. Replacing a general connector with a custom one, and putting several behind one entry point, is where the larger gain is, and it is a build job. This needs someone technical: a developer inside the company or outside help. The plan above is written so that person can start from it.

Do not present trimming as the whole answer, and do not suggest the person can build a custom connector themselves unless they have said they write software.

### Done when

- Every connector has a decision.
- The trims are done or listed with who will do them.
- Each connector marked replace has the fields and actions the work needs written down, and the plan says who could build it or that nobody is named yet.
- The person has been told which part is hard.

### Mark blocked when

- The weight step is blocked, so there is nothing to base a replace decision on. Record trim and keep decisions and mark this step `blocked`.
- The person cannot decide without the teams that use the connectors.

Having nobody technical to build a replacement does not block this step. Record it in the plan as "not yet named".

### Summary to report

State the number of connectors under each decision and that the hard part was named. Example: "Plan recorded: 9 connectors to trim (6 done today), 14 keep, 3 replace. The 3 replacements need someone technical to build; nobody named yet. Sessions now load 15 connectors."
